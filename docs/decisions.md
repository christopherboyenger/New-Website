# Product and engineering decisions

Decisions made where the specifications (`docs/spec/`) are silent, conflicting, or explicitly ask for a decision. Feature-area decisions live in `docs/decisions/<area>.md`. Each entry states what is **observed**, **documented**, or **proposed**; nothing here claims to be recovered reference behavior.

| ID | Decision | Rationale / spec reference |
|---|---|---|
| DEC-001 | The product is a separate brand. Placeholder name "Acme Creators" / wordmark "acme" comes from `src/config/site.ts` (env-overridable). No reference name, logo, claims, endpoints or account data are used. | production-requirements.md §1 and §3 (never reuse Noise endpoints/keys); production-ui-plan.md "Asset requirements". **Choose the real product name before launch.** |
| DEC-002 | Persistence is Postgres via Drizzle ORM. Local development and tests use embedded PGlite; production requires `DATABASE_URL`. | production-requirements.md §1 (transactional database). No provider is provisioned yet; the code is provider-neutral Postgres. |
| DEC-003 | Authentication is first-party email + password (scrypt), database-backed sessions (token digests only), email verification, password reset, login rate limiting, and recent-auth step-up for sensitive actions. | production-ui-plan.md routes `/auth/*` ("no fake login"). Can be swapped for a provisioned identity provider later; authorization is independent of the auth mechanism. |
| DEC-004 | Email is sent through an adapter (Resend HTTP API when `RESEND_API_KEY`/`EMAIL_FROM` are set). Without a provider, messages are recorded with status `provider_unconfigured` and the UI says they were not delivered; `/dev/outbox` shows them in development only. | production-ui-plan.md "Messaging/invitations": queued/sent/failed from server state. |
| DEC-005 | Role matrix: Owner = everything except ownership transfer (primary owner only). Member = read workspace/reporting, edit playbook drafts, use messages. Members cannot create/activate/pause campaigns, publish playbooks, see billing, manage integrations/tokens/members, or edit branding/ad settings. Owners manage only Members; the primary owner manages Owners. | Documented: Member "does not control campaigns or billing"; owners manage below their level; only primary owner transfers (team-and-roles). The remaining Member cells are proposed. |
| DEC-006 | Plan gates (Unlimited only): manual pricing, CPM cap, demographic targeting (age/gender/metros), creator-level minimum above "All creators", creator approval, dedicated accounts, creator messaging. Enforced in server commands. | Observed "Requires … Unlimited" badges L18–L22; production-requirements.md §4.2. |
| DEC-007 | Commercial terms live in `src/config/commercial-policy.ts` with `decided: false`. One display name per plan ("Standard"/"Unlimited") everywhere. The $500 matching offer and the $5 validation charge are **disabled** until the business decides them; the payment disclosure string is shared by onboarding, pricing and billing. | Reference showed conflicting terms (B07 "nothing up front" vs L13 "$5 non-refundable validation credit"; "Standard" vs "Basic"). production-requirements.md §2 "Billing and credits". |
| DEC-008 | Reach forecasts are a separate service that currently returns "Reach estimate unavailable". No formula is derived from screenshot values. | production-ui-plan.md "Budget"; build spec "Onboarding estimator uncertainty". |
| DEC-009 | Templates declare a format; a playbook's format follows its campaign; a template of another format is rejected, never converted. | Evidence audit item 6 (Slideshow → Greenscreen mismatch is not a conversion rule). |
| DEC-010 | Campaign primary hashtags are normalized (no `#`, lowercase, `[a-z0-9_]{2,50}`) and unique across the whole platform, so a post matches exactly one campaign. | Documented: primary hashtag is campaign-unique and required for matching. |
| DEC-011 | Daily report rows are sparse (only days with data). Per-day `posts`/`creators` count distinct approved posts/creators with a metric row that day; totals deduplicate across the range. Post `spend` in the drilldown is spend within the requested range (like `range_views`). Default `order` is `desc`. | API docs leave these unspecified. |
| DEC-012 | Blended installs: if any store (App Store/Play) reported that day, blended = sum of store actuals (`store`); otherwise the overall estimate (`estimated`); totals `installs_source` = `store`/`estimated`/`mixed`. Raw series are returned separately and never added to estimates. | Documented precedence; exact one-platform rule unspecified. |
| DEC-013 | Rolling view counters (Home/Live) are computed from cumulative metric observations (correction-safe deltas). A workspace with no approved posts shows a confirmed 0; posts with no metric source show "unavailable". | production-ui-plan.md Home/Live rows; no fabricated activity. |
| DEC-014 | Platform onboarding omits reference position 5 (never observed); progress counts implemented screens only. Role choices are the four observed labels (Founder, Creator, Operations, Other); the two hidden labels are not invented. | production-ui-plan.md "Onboarding implementation contract". |
| DEC-015 | Campaign targeting defaults are "All countries / All platforms / All creators" (empty lists). Daily mode budget is an average target (min $50/day), not a cap. | Observed L17–L20; documented dynamic minimum $50. |
| DEC-016 | Tenant credentials are sealed with AES-256-GCM (`CREDENTIALS_ENCRYPTION_KEY`), with associated data binding org/installation/provider/generation. Without the key, provider secrets are refused. | production-integration-contracts.md §4 "Custody". |

Readiness of every external capability is reported by `src/server/readiness.ts`; see `docs/readiness.md`.
