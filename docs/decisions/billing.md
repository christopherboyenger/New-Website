# Billing decisions

Decisions made for the Billing page (`/home/[org]/billing`), provider-hosted payment setup and plan upgrade, the Stripe webhook (`/api/webhooks/stripe`) and the billing ledger, where the specifications are silent, conflicting, or explicitly ask for a decision. Format: `ID — decision — rationale — spec reference`. Nothing here claims to be observed reference behavior; L13 was inspected without opening a payment form, changing the threshold, upgrading, or seeing payment success or failure.

- **BILLING-01** — Current balance means campaign spend not yet charged: Σ `campaign_spend` − Σ `cash_charge` that paid campaign spend − Σ credits applied (negative entries in `subscription_credit` / `matching_credit` / `validation_credit`). Plan-subscription payments (`ref_type = stripe_subscription_invoice`) never reduce it. The value is shown as computed and never clamped. A workspace with no ledger entries shows a confirmed $0.00. — The reference shows a "Current balance" and a threshold with no definition. production-requirements.md keeps spend, cash charges and credits in separate ledgers. — L13; production-requirements.md "Billing and credits"; production-integration-contracts.md §6.
- **BILLING-02** — Credit ledgers use signed entries: positive amounts grant credit and negative amounts apply it. Remaining credit = granted − applied. — One convention for every credit ledger, with no mutable balance column. — production-integration-contracts.md §6 ("immutable entries/corrections").
- **BILLING-03** — The "Matching credits remaining" figure and any matching-credit copy render only when `commercialPolicy.matchingCredit.enabled` is true (currently false). The reference's "Every $50 you spend earns a $50 credit" line is not shown. — DEC-007. Eligibility, expiry and drawdown are undecided. — L13; evidence audit item 4.
- **BILLING-04** — The charge threshold options come from `commercialPolicy.billingThresholdOptionsCents` and use the onboarding card descriptions (`billingThresholdOptions()`). The editor says the threshold is "a monetary increment, not a schedule" and that changing it never charges. Only owners can save it (`billing:manage`), with an optimistic check on `organizations.version`. Values the policy does not offer are rejected. — Evidence audit item 4: "$10/$25/$50 are charge thresholds, not scheduled time intervals". — B06; L13.
- **BILLING-05** — The page shows one disclosure, `paymentSetupDisclosure()`, in a confirmation dialog before every card action (add, update, start over) and in the "Set up billing" empty state. The reference's "$5 non-refundable validation credit" text is not shown while `paymentSetupValidationCharge.enabled` is false. — DEC-007: the same disclosure appears in onboarding, pricing and billing. — L13 vs B07; evidence audit item 4.
- **BILLING-06** — Card setup uses Stripe Checkout in `setup` mode with `payment_method_types: ["card"]`, which never charges. Sessions expire after 60 minutes. Return URLs are absolute URLs on `site.appUrl`, limited to `/onboarding` or a path inside the caller's own workspace (`/home/<slug>/…`). Any other path returns an `error` result and creates no session. The return adds `?setup=returned`/`canceled` and only changes the copy ("we're confirming your card"), never the stored status. — production-requirements.md: "A payment-return URL is not settlement proof"; contracts §6: "Hosted session return URLs are allowlisted".
- **BILLING-07** — Starting setup marks the account `pending` only when no confirmed card exists (from `none`/`failed`/`requires_action`/`pending`). While a replacement card is set up, a `ready` card stays `ready`, so publishing is not blocked by an update in progress. Starting again expires the previous unfinished session at the provider first, which is best effort. — The spec requires a pending state but does not cover card replacement. A confirmed card is still valid provider truth. — production-ui-plan.md "Payment uncertain".
- **BILLING-08** — "Check again" (`refreshPaymentStatus`) retrieves the latest setup session and its SetupIntent from the provider and applies the same effect a webhook would: `complete` → apply the intent, and `expired` while pending → `none`. If the provider is unreachable, the stored status is shown with a message. This keeps a workspace from staying pending forever when webhooks are delayed or not configured. — production-ui-plan.md "Payment uncertain: refresh/status recovery"; contracts §6.5 ("retrieve current provider objects").
- **BILLING-09** — When a card is confirmed, it becomes the customer's `invoice_settings.default_payment_method`, which off-session threshold charges will use. — A threshold charge needs a default method. This is an idempotent provider write made only after provider confirmation.
- **BILLING-10** — A failed or unfinished attempt to replace a card never downgrades a `ready` card. `invoice.payment_failed` sets `failed` only when a fresh retrieve shows the invoice is still unpaid. `payment_method.detached` clears the card only when the detached method is the one on file. — Out-of-order and duplicate deliveries must converge to provider truth. — production-requirements.md §4.8.
- **BILLING-11** — The plan comes from stored provider subscriptions. It is Unlimited while any subscription to `STRIPE_UNLIMITED_PRICE_ID` is `active`, `trialing` or `past_due`, and Basic otherwise. Each `customer.subscription.*` and subscription-mode `checkout.session.completed` event re-retrieves the subscription, upserts `billing_subscriptions` and recomputes `organizations.plan_id`. Plan changes do not bump `organizations.version`, so open settings forms stay valid, and are audited as `billing.plan.changed`. — The order in which Stripe delivers events is not guaranteed, so the retrieved object decides. `past_due` keeps the plan during the provider's retry period. — contracts §6.5; production-requirements.md §4.8.
- **BILLING-12** — Downgrade policy for existing gated campaign settings: on downgrade to Basic, campaigns keep their stored Unlimited-only settings and keep running unchanged. Any command that changes those settings must pass `assertEntitled` against the new plan, so gated values cannot be created or edited until the workspace upgrades again. Nothing is rewritten or paused automatically. — production-requirements.md §4.2 requires an explicit policy. Silently changing live campaign targeting or pricing would change spend without a user action (non-negotiable 5). — src/domain/entitlements.ts.
- **BILLING-13** — Upgrade uses a Checkout `subscription` session for `STRIPE_UNLIMITED_PRICE_ID`. It is available only when both the secret key and the price ID are configured, and otherwise says "Upgrades aren't configured on this deployment yet." A confirmation dialog first shows the plan terms from `commercialPolicy.plans.unlimited` and says the hosted checkout shows the final amount. The provider's price is the amount actually charged. — Plan names and prices come only from the commercial policy. The charge itself is made by the provider's hosted page after explicit confirmation. — DEC-007; non-negotiable 4.
- **BILLING-14** — Subscription invoices are recorded only as `cash_charge` (`stripe_subscription_invoice`). No `subscription_credit` is granted automatically while `commercialPolicy.decided` is false, even though the policy text says the $99 is credited toward campaign spend. — Contracts §6: the $99 credit policy must be decided before it moves money in the ledger.
- **BILLING-15** — Unlimited workspaces with a provider subscription get "Manage plan", which opens the Stripe customer portal (change or cancel happens on the provider's page). — The task needs a cancel and downgrade path, and building in-app cancellation would duplicate provider dunning and proration rules.
- **BILLING-16** — Webhook ingestion: the raw body is capped at 512 KB, the signature is verified with the SDK's default tolerance, and an event whose `livemode` differs from the configured key's mode is rejected with 400 and not stored. The inbox is unique on provider + environment + event ID. Redelivery of an event already `processed` or `quarantined` returns 200 with no effect. Redelivery of a `failed` event is processed again: attempts are incremented, and effects stay idempotent through effect keys and fresh retrieves. A processing error is stored as a provider error category (no payloads) and answered with 500, so Stripe's retry schedule acts as the retry and backoff mechanism because no background worker exists yet. A missing signing secret returns 503 (retriable). — Contracts §6 steps 1–6.
- **BILLING-17** — Tenant routing uses only `billing_accounts.provider_customer_id` joined to `billing_provider_state.environment` (the key mode that created the customer). Unknown customers, or customers mapped in the other mode, are `quarantined`. A retrieved object whose customer differs from the mapped one (`mismatch`) is also quarantined. `metadata.org_id` and `client_reference_id` are sent for operator reconciliation only and are never read for routing. — Contracts §6.4.
- **BILLING-18** — The provider customer is created on first need with idempotency key `customer_create:<orgId>:<mode>`. If the key mode changes (test → live), a new customer is created and the old card status is reset, because a test-mode card is not usable in live mode. Every outbound call (customer, setup session, upgrade session) is recorded in `provider_operations` before the call and marked `succeeded`/`failed` afterwards. — Contracts §6: "Persist command intent before calling Stripe".
- **BILLING-19** — Business information (name required; optional address line 1–2, city, state/region, postal code, country, and tax ID) is stored on `billing_accounts` and is owner-only. A country is required once any address line, city or postal code is given. Saves use a revision hash of the stored values, because `billing_accounts.updated_at` also changes on webhook updates. Details are not yet synced to the provider customer. — The reference shows only "Add business information". The field set is a proposed minimum for receipts.
- **BILLING-20** — Activity tabs follow the reference labels. "Payment activity" lists `cash_charge` entries, and "Credits" lists the three credit ledgers. Both are filtered by the shared UTC `DateRangePicker` (`from`/`to`), use `tab` and `page` in the URL, and show 20 rows per page. With no payments and no usable card, the Payment activity empty state is "Set up billing" with the disclosure and "Add a payment method". — L13 control names; dates are UTC calendar days like the reporting pages (DEC-011).
- **BILLING-21** — Members see a page that explains billing is owner-only and shows no billing data (plan, balance, card or business details). Every action re-authorizes server-side with `billing:manage`, or `billing:view` for "Check again", and members get `forbidden` before any provider call. — DEC-005; contracts §8 "Member calls billing/session route directly".
- **BILLING-22** — When `capability("payments")` is not configured, the page shows a not-configured notice, hides card and upgrade actions, and says that nothing on the page charges. When payments are configured but `payment_webhooks` is not, a warning explains that confirmations need "Check again". — Non-negotiable 2; src/server/readiness.ts.
