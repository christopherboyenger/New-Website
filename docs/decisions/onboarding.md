# Onboarding and authentication decisions

Decisions made for the auth pages (`/auth/*`) and the platform brand onboarding wizard (`/onboarding`) where the specifications are silent, conflicting, or explicitly ask for a decision. Format: `ID — decision — rationale — spec reference`. Nothing here claims to be recovered reference behavior; reference indices are kept only as an evidence map (`referencePositions` in `src/domain/onboarding.ts`).

- **ONBOARDING-01** — Screens, in order: role → overview → referral → brand → budget → summary → format → template → billing threshold → payment (10 screens; the progress bar has 10 segments). — Reference position 5 was never observed and is omitted, so progress counts only implemented screens. — DEC-014; production-ui-plan.md "Onboarding implementation contract".
- **ONBOARDING-02** — Role screen copy is original ("What best describes your role?" / "We’ll use this to tailor your workspace."), with only the four observed labels (Founder, Creator, Operations, Other). — The A04 title and subtitle are cut off; completing them would present a guess as observed copy. — A04; DEC-014.
- **ONBOARDING-03** — Referral follow-ups (proposed): "I have a code" requires a code (1–40 characters: letters, digits, `-`, `_`); "Other" offers an optional free-text detail (≤120 characters). Follow-up answers are dropped when the source changes. Answers are stored in the draft and written to the `onboarding.complete` audit entry; codes are not checked against any promotion because no promotion program exists. — The captures do not show what follows these choices; the plan asks for server validation and explicit optionality. — A08; production-ui-plan.md "Referral".
- **ONBOARDING-04** — Brand basics: all three fields are required. Name ≤80 characters; website, App Store or Google Play link ≤300 characters (a domain or http(s) URL); description 1–500 characters. Limits match `brandBasicsSchema` in `src/server/organizations.ts`. — B01’s Next was disabled with a blank description (suggestive, not proof); the description feeds template recommendations, and one rule set keeps client and server consistent. — B01; production-ui-plan.md "Brand".
- **ONBOARDING-05** — The first successful brand-basics save creates the workspace with `createOrganization`, exactly once per draft instance (guarded by `onboarding_org_claims`). Later brand saves during onboarding update that workspace’s name, links and short description; the slug is not changed. — A persisted organization draft is required, and the workspace must never be duplicated by double submits or concurrent tabs. — production-ui-plan.md route `/onboarding`.
- **ONBOARDING-06** — Daily budget: whole dollars, $50–$5,000 per day; the slider moves in $10 steps and the number field accepts any whole-dollar value. The default is $50, the documented minimum, so the UI never nudges spend upward. The value becomes the first campaign’s daily average target. — The reference shows one $1,000 sample and no range. $5,000 is a proposed onboarding cap; the campaign form allows larger budgets. — B02; DEC-015.
- **ONBOARDING-07** — The reach estimate comes only from `forecastReach()`, re-requested 400 ms after budget changes, for default targeting and the saved format (Slideshow, the first listed format, until a format is chosen, because the budget screen comes before the format screen). While the service is unavailable, the screen says "Reach estimate unavailable" with the service’s reason and shows no numbers. — The reference’s 20,000,000 views and 8,333 creators are not a formula. — DEC-008; production-ui-plan.md "Budget".
- **ONBOARDING-08** — The budget screen’s billing note says "Your daily budget is an average target, not an upfront charge." followed by `paymentSetupDisclosure()`. It replaces the reference’s "You only pay for the views you get… never charge your full budget upfront". — Billing copy must match the commercial policy in every surface. — B02; DEC-007.
- **ONBOARDING-09** — Reference position 7 (reassurance) becomes "Here’s your plan so far": a summary of the saved brand and budget, with "Change" links back to those screens, and the reach estimate stated as unavailable. There is no "very achievable" claim, and the illustration is original. — B03; production-ui-plan.md "Reassurance".
- **ONBOARDING-10** — The format screen title is "Choose a content format" (B04’s title is not visible). The observed subtitle "Real examples from campaigns running right now…" is not used because the cards show neutral illustrations, not real examples. Format descriptions are the observed ones. — B04; production-ui-plan.md "Asset requirements".
- **ONBOARDING-11** — The template screen lists `templatesForFormat(format)` under "Templates for <Format>". It does not say "Recommended for your brand", because no recommendation engine exists, or "You can access these inside the builder", which is unverified. A format change keeps a compatible template; otherwise the template is cleared and the template screen explains why. Templates are never converted. — B05 capture mismatch; DEC-009.
- **ONBOARDING-12** — Billing threshold options come from `commercialPolicy.billingThresholdOptionsCents`, with the observed card descriptions. `defaultBillingThresholdCents` ($50) is preselected, matching B06’s apparent selection. The lead omits "you can change this any time" because no settings screen changes the threshold yet. — B06; DEC-007.
- **ONBOARDING-13** — Payment: "Add payment method" calls `startPaymentMethodSetup()` (provider-hosted, returning to `/onboarding`) and reports `redirect`, `not_configured` or `error` as returned. The `pending`, `requires_action` and `failed` states are shown from stored provider-confirmed status. Finish is enabled only when that status is `ready`. The disclosure uses `paymentSetupDisclosure()` instead of B07’s "nothing up front". — B07; DEC-007; production-ui-plan.md "Payment".
- **ONBOARDING-14** — Completion (Finish or "I’ll finish later") creates an inactive campaign named "<Brand> <Format>". Its primary hashtag is derived from the brand name and made unique (stem, stem2 … stem25, then a random suffix) via `isHashtagAvailable`. It also creates a draft playbook from the chosen template, stores the billing threshold on the workspace, marks the draft complete (setting `deferredPaymentAt` for "later"), and opens the playbook editor. Completion is idempotent: double submits and retries reuse the same campaign and playbook. Nothing is activated, published or charged. — production-ui-plan.md "Payment: … operational ‘finish later’ path to a draft workspace".
- **ONBOARDING-15** — Persistence and navigation: Next saves only the current screen’s fields (other submitted keys are ignored) and refuses to skip an incomplete earlier screen. The server records the furthest screen reached; a reload resumes there, but never past an incomplete screen. Back does not save and keeps unsaved edits. Back appears on every screen after the first, although the overview capture shows none, for consistent keyboard and screen-reader navigation. — production-ui-plan.md route `/onboarding` ("resume and previous-step state").
- **ONBOARDING-16** — `/onboarding` sends members of any workspace to `/home`. `/onboarding?new=1` starts a fresh draft for an additional workspace (with a new draft ID, so it may create its own workspace) and replaces the completed draft on its first save. A completed draft whose workspace the user no longer belongs to restarts instead of redirecting, which avoids a `/home` ↔ `/onboarding` loop. — Additional workspaces need an explicit entry point; the workspace switcher links to `?new=1`.
- **ONBOARDING-17** — The agent dialog has Claude, ChatGPT and Gemini tabs. While `capability("mcp")` is not configured, it says this product’s MCP server is not deployed and shows no URL. When configured, it shows this deployment’s `mcpServerUrl()` with copy feedback. "Questions?" is a `mailto:` link, rendered only when `site.supportEmail` is set. — A04; production-ui-plan.md "Agent dialog".
- **ONBOARDING-18** — The green promotion banner renders only when `commercialPolicy.matchingCredit.enabled` (currently false); its copy is derived from the policy cap. — DEC-007.
- **ONBOARDING-19** — Auth navigation: `?next=` is honored only when `isSafeReturnPath` accepts it and it does not point into `/auth`. Signed-in visits to sign-in or sign-up go to that `next` or `/home`. Sign-up continues to `next` or `/onboarding`. Sign-in and sign-up preserve `next` in their cross-links, and `?email=` only prefills the field. — production-ui-plan.md routes `/auth/*` ("safe return URL").
- **ONBOARDING-20** — Verification links do not verify on page load: the person submits "Verify email address", so mail scanners and link prefetchers cannot consume the one-time token. Without a token, a signed-in unverified user sees the real status of their latest verification email (from the outbox) and can resend, limited to 3 per hour. `provider_unconfigured` is stated plainly; the development outbox link appears only when dev tools are enabled. — DEC-003; DEC-004.
- **ONBOARDING-21** — Password reset requests get the same answer whether or not the account exists. The answer varies only with whether this deployment can send email, which is a deployment property, not an account property. An invalid or expired reset link replaces the form with "Request a new reset link". After a reset the user is signed in on this device and other sessions are revoked, and the page says so. — DEC-003.
- **ONBOARDING-22** — Mobile layout (below 640px): one-column cards, full-width Next, and a textual "Step X of Y" beside Back. The action bar follows the content rather than sticking, so it never covers fields or rides above the on-screen keyboard. From 640px up it sticks to the bottom like the reference. — production-ui-plan.md "Responsive" (new design).
- **ONBOARDING-23** — Overview rows use icons in pale squares instead of the reference’s emoji artwork. All wizard illustrations are original neutral geometry with no people, faces, creator media or numbers. — A05; production-ui-plan.md "Asset requirements".
