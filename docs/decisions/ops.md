# Operator console and earnings primitives — decisions

Format: `OPS-NN — decision — rationale — spec reference`. These are product/engineering decisions for this build, not observed reference behavior (the reference operator tooling was never observed).

- OPS-01 — An operator is a signed-in, enabled user whose **verified** email is listed in `OPERATOR_EMAILS`. Everyone else (signed out, unlisted, unverified, disabled) gets the generic 404 from every `/ops` route, and operator Server Actions return `not_found`. Signed-out visitors are not redirected to sign-in, so the console's existence is not disclosed. — Contracts require an explicit operator role with no implicit employee access; a 404 matches the tenant-isolation rule used elsewhere. — production-integration-contracts.md §"Roles" (Operator row); CLAUDE.md non-negotiable 3.
- OPS-02 — Operator status grants only the console views and post-review commands. It does not make the operator a workspace member, and the console links to no workspace, billing or integration page and reads no credential tables. Per-case/organization operator scoping is not built yet (allowlist = all organizations). — Contracts require "case/organization scope"; the allowlist is the agreed first step. — production-integration-contracts.md §"Roles".
- OPS-03 — Post review is a one-way transition from `submitted` to `approved` or `rejected`, enforced with a conditional update (`WHERE review_status = 'submitted'`) inside a transaction. A repeated or concurrent decision changes nothing and returns `conflict` ("already approved/rejected"), so each post gets exactly one decision and one audit entry. Reversal/appeal of a decision is not built. — Spec asks for an audited, reversible correction process; until its rules are decided, decisions are not silently overwritten. — production-requirements.md "Review, metric ingestion, and earnings".
- OPS-04 — Rejection requires a reason code from a fixed list (missing primary hashtag, platform not targeted, creator not admitted, account not verified, off brief, content guidelines, duplicate, unavailable, other); a note up to 500 characters is optional except for "Other". `posts.review_reason` stores readable text (`<label> — <note>`, or the note alone for "Other"); the code, note, previous status and a snapshot of the automatic check results go into the audit record (`ops.post.approve` / `ops.post.reject`, orgId = the post's organization). — Spec requires retained rejection reasons and review audit; the reason list is proposed. — production-requirements.md §"Creator portal" ("Retain rejection reasons…").
- OPS-05 — Automatic checks (primary hashtag present as a whole tag, case-insensitive; platform within campaign targeting, where an empty list means all platforms; creator admission approved, or not required by the campaign and not rejected/removed; campaign active — shown as a warning, since an approved post on a paused campaign simply earns nothing; linked social account verified, owned by the submitting creator and on the post's platform) are informational. They never approve or reject on their own. — "Rule automation can cover objective requirements; ambiguous content needs an operator queue." — production-requirements.md "Review…".
- OPS-06 — The review queue lists `submitted` posts across all organizations, oldest submission first (ties by ID), 20 per page, paginated on the server. Campaign, playbook and admission joins are constrained to the post's own organization. — Fair FIFO handling; tenant-qualified joins. — CLAUDE.md non-negotiable 3.
- OPS-07 — `/ops/webhooks` shows only `quarantined`/`failed` inbox rows with provider, environment, event type, event ID, received time, attempts and a 240-character error preview. Payloads are never selected. Read-only: replaying or resolving events is not built. — Payloads can contain customer data; reconciliation tooling needs its own decided workflow. — production-integration-contracts.md §"Webhooks" (quarantine for reconciliation).
- OPS-08 — `/ops/leads` is read-only (email, company, budget band, CTA, step reached out of 3, created), newest first. Lead exports and edits are not provided. — Minimal PII exposure. — production-ui-plan.md acquisition.
- OPS-09 — `src/domain/earnings.ts` has no default policy: `computeEarning(policy, input)` requires an explicit `EarningPolicy` (version ID, integer cents per 1,000 valid views, per-post lifetime cap or explicit `null`) and rejects anything malformed. `src/server/ops/earnings.ts` returns no configured policy, so `earningPolicyConfigured() === false` and no earning job may run. The console lists the open decisions (`earningPolicyOpenDecisions`). — The spec forbids enabling earning jobs before valid-view, rate, caps, windows, rounding, pause/reactivation, reversal and funding policies are decided. — production-requirements.md "Review, metric ingestion, and earnings"; reference-build-specification.md §5 acceptance checks.
- OPS-10 — Earning mechanics: valid-view growth = `counterDelta(previous, current)` (the first observation only sets the baseline; a decreasing counter yields 0); amount = floor(delta × rate / 1000) in whole cents using exact integer arithmetic; then limited to `cap − alreadyEarned` (never below 0); unapproved posts and non-active campaigns (paused/inactive/unattributed) earn 0. The effect key is `earning:<postId>:<windowStartISO>/<windowEndISO>`, deliberately independent of the policy version so a policy change cannot pay the same window twice. — Correction-aware deltas, "paused campaigns earn nothing", idempotent ledger effects. — production-requirements.md "Review…"; reference-build-specification.md "Campaign" (pause stops earning for all posts); §5 EarningEvent (idempotency key).
- OPS-11 — No new tables were needed: review state uses the existing `posts.review_*` columns and the shared audit log. `src/server/db/schema/ext-ops.ts` was not created. — Avoid schema churn. — CLAUDE.md "Database".
