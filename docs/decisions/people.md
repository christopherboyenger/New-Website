# People area decisions (Creators roster, Members + invitations, Branding)

Format: `PEOPLE-NN — decision — rationale — spec reference`. These are product decisions made where the spec is silent or conflicting. None of them is claimed to be observed reference behavior unless a live state is cited.

## Creators roster

- PEOPLE-01 — A creator is on an organization's roster if any of these holds: there is an `org_creators` row, there is an approved `campaign_memberships` admission in the org, or there is an approved post in the org. Creators who only qualify through admissions or posts count as active. Removing one inserts the `org_creators` row. All queries are scoped by the authorized `orgId`. — The reference roster lists creators who joined a campaign. Approved posts are evidence of the same relationship. — build spec L10; production-requirements §4.1.
- PEOPLE-02 — Table metrics (Posts, Views, Likes, Comments) are lifetime sums over the creator's approved posts in this org only. When no post has an observed counter, the sum shows "—", never 0. Platforms and Accounts count the creator's linked social accounts. — The table has no date range, and numbers must never be fabricated. — build spec L10; CLAUDE.md non-negotiable 2.
- PEOPLE-03 — Summary cards use a window of the last 30 UTC days and count only active roster creators and approved posts. **Most Views** is the creator with the most views earned in the window, from `post_daily_metrics`. **Most Viral** is the creator of the single post with the most lifetime views among posts published in the window. **Most Engaging** is the creator with the highest (likes + comments) ÷ views over posts published in the window, with at least 1,000 views in total. A card with no qualifying data shows "No data yet". Each card states its definition. — The reference shows the three cards but not their definitions. — build spec L10.
- PEOPLE-04 — Posting activity is an 8-week (56 UTC days) heatmap that counts approved posts per day, using the posted time or, when that is unknown, the submission time. It has a text summary for assistive technology. — The task asks for a compact per-day heatmap. — production-ui-plan creators row.
- PEOPLE-05 — Remove and Restore need `creator:manage` (Owners) and a confirmation. Remove sets `org_creators.removed_at` and `removed_by_user_id` and writes an audit entry. Consequences: the creator moves to the Removed tab and is left out of the summary cards. Their past posts and metrics stay in reporting. Existing campaign admissions are unchanged. They must not be admitted to the org's campaigns again until restored. This last rule is exposed as `isCreatorRemovedFromOrg(orgId, creatorId)`, and campaign admission (another area) must call it. — Removing a creator must not erase history. — build spec L10.
- PEOPLE-06 — The creator detail drawer is a proposed layout. It is opened with `?creator=<id>` and shows the profile (level, country, on roster since), social accounts with their verification status, the campaigns they were admitted to, and the 10 most recent posts in this org with review status. A creator who is not on the authorized org's roster is not shown (same as not found). — The reference detail view was not captured. — build spec L10 unknowns.
- PEOPLE-07 — Roster URL state is `tab, q, campaign, level, platform, sort, order, page, creator`. The page size is 25. A page past the end shows the last page. — Views can be shared and survive a reload. — production-ui-plan creators row.

## Members and invitations

- PEOPLE-08 — The invite dialog adds a role picker that is limited to `grantableRoles(actor)`: the primary owner can invite Owners or Members, and other Owners can invite Members only. The captured L32 dialog showed no picker. When only one role is grantable, that role is the one sent. — DEC-005 rank rules need an explicit role on every invitation. — build spec L32; DEC-005.
- PEOPLE-09 — Only an inviter with a verified email address can create or renew invitations. — This stops unverified accounts from using the product to send email. — production-requirements §4.1.
- PEOPLE-10 — Invitations expire 7 days after they are created or renewed. "Expired" is derived from `expires_at` and is not stored. — The spec gives no TTL. 7 days is a common, conservative choice. — build spec "Documented roles and access lifecycle".
- PEOPLE-11 — Rate limits: 30 invitation emails per inviter per hour and 100 per workspace per day, with at most 10 addresses per request. — These limit abuse while allowing a normal team setup. — production-requirements §4.1.
- PEOPLE-12 — Each email has at most one open invitation per org. Inviting an address that already has a live invitation reports "already invited". Inviting an address whose invitation expired or was revoked renews that row with a new token. Inviting a current member reports "already member". Concurrent invites for the same address are serialized with an advisory lock. — Duplicate links would be confusing and harder to revoke. — task spec.
- PEOPLE-13 — The token is `generateToken()` (32 random bytes). Only `tokenDigest(token, 'invitation')` is stored. Renewing an invitation issues a new token, so old links stop working. — If the database leaks, it holds no usable links. — production-integration-contracts §2.
- PEOPLE-14 — The dialog reports what happened to each invitation: sent, failed, or not delivered because no email provider is configured. Only when an email was not sent does the response that created the invitation include the invite link, so the inviting Owner can copy it once. The link is never stored in plain text and cannot be shown again (renew to get a new one). Security reasoning: the inviter already has the right to grant access to that address, the token is still bound to the invited email (it can be accepted only by an account with that verified email), and it expires after 7 days or on revocation. — Without this, a deployment without email could not add teammates, and the product must not claim an email was sent. — CLAUDE.md non-negotiable 2.
- PEOPLE-15 — Pending Invites (with Expired and Revoked rows) is shown only to users who can invite (Owners). Members see the team list read-only, with the reason shown. Owners can revoke and renew invitations only for roles they could grant. — Invitee emails are management data. — DEC-005.
- PEOPLE-16 — Removing a member deletes the membership immediately. Every page and action re-reads membership, so access ends on the next request. Content they created stays with the org. Their "last workspace" pointer is cleared. The action is audited. — build spec "Documented roles and access lifecycle".
- PEOPLE-17 — Primary ownership transfer is available to the primary owner only. The target must already be an Owner. The primary owner re-enters their password every time (`confirmPassword`, then `markRecentAuth`). A compare-and-set on `primary_owner_user_id` guards against races. The previous primary owner stays an Owner. The action is audited. — DEC-005.
- PEOPLE-18 — Any member or non-primary Owner can leave the team after a confirmation. The primary owner must transfer ownership first, and the Danger zone explains this. — build spec L12/L14.

## Invitation acceptance (/invitations/[token])

- PEOPLE-19 — Unknown, expired, revoked and already-used tokens all show one generic "invalid or expired" message. Opening the link never joins the workspace; the person has to press "Join". If the person who accepted an invitation opens it again, they are sent to the workspace. — This avoids leaking invitation state, and makes acceptance an explicit choice. — production-integration-contracts §2.
- PEOPLE-20 — A signed-in user with a different email is refused with "This invitation was sent to <masked email>" and offered "Sign out and switch account". The email is masked as first letter, •••, last letter, @domain. A matching but unverified email is asked to verify first (`/auth/verify`). Acceptance is idempotent: an existing membership keeps its role. The page sets `referrer: no-referrer` and `noindex` because the token is in the URL. — task spec.

## Branding

- PEOPLE-21 — Brand category taxonomy (application-defined, alphabetical with Other last): Apparel & Fashion, Apps & Software, Automotive, Beauty & Personal Care, Books & Publishing, Education, Entertainment, Finance, Fitness, Food & Beverage, Gaming, Health & Wellness, Home & Garden, Music, Parenting & Family, Pets, Sports, Technology & Electronics, Travel & Hospitality, Other. Up to three categories, which must be distinct. Stored values outside the list are dropped from the form. — The reference option list was not captured. — build spec L12.
- PEOPLE-22 — The brand hashtag is stored without "#" and in lowercase, with 2–50 characters from `[a-z0-9_]`. The color is `#rrggbb` or empty (the preview then uses a neutral default, never the product accent). — Hashtags are matched case-insensitively on platforms. — build spec L12.
- PEOPLE-23 — Links: Website accepts any http(s) URL with a real host (a bare domain gets `https://`). App Store must be on `apps.apple.com`. Android must be on `play.google.com`. URLs with credentials are rejected. — The tabs name specific stores. — build spec L12.
- PEOPLE-24 — The description is sanitized on the server with sanitize-html (`src/domain/rich-text.ts`). Allowed tags: h2, h3, p, br, strong, em, u, ul, ol, li, and a with `https:` or `mailto:` only (always `rel="noopener noreferrer" target="_blank"`). Unsafe links are unwrapped and keep their text. The 1,000-character limit counts visible text characters (code points), not markup. — Formatting must not use up the allowance. — build spec L12.
- PEOPLE-25 — Logo and cover uploads need `media_storage`, which is not provisioned. The page shows a not-configured notice with the size guidance (logo ≥256×256, cover ≥800×800, PNG/JPG) and uses initials and a neutral color as placeholders. — Never fake an upload. — readiness `media_storage`.
- PEOPLE-26 — The live creator-facing preview shows only branding fields (name, hashtag, categories, description, links). It does not show sample rates, earnings or creator-level economics, which the reference preview displayed. — These come from campaigns, and showing samples would fabricate numbers. — production-ui-plan branding row.
- PEOPLE-27 — Save is disabled until the form changes. Saves send `organizations.version`, and a stale version is a conflict that asks for a reload (never an overwrite). Only Owners can edit (`branding:edit`). Others see the form read-only, with the reason shown. Saving revalidates the workspace layout because the name appears in the shell. — CLAUDE.md optimistic concurrency; DEC-005.
